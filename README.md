# Heat Priority Engine

**Phoenix transit heat operations** — FortyGuard Hackathon '26

> Find where Phoenix transit riders would accumulate the greatest estimated heat
> exposure — and where FortyGuard reveals heat that is unusually severe for the
> surrounding area.

The project is now a connected operations product rather than a single
dashboard: monitor the verified heat surface, build a defensible priority plan,
dispatch field missions, capture observations, require human review, compare
baselines, and export an auditable decision package. The field workflow is a
session-isolated demonstration; it never disguises demo input as source data and
never changes the thermal ranking without review.

Two questions, so two metrics, reported on two axes and **never blended into a
weighted score**. There is no weight slider anywhere in this product.

> **Read [`docs/findings-provenance.md`](docs/findings-provenance.md) before
> quoting any number from this repository.** The default Downtown pilot uses a
> committed real FortyGuard snapshot; Central and Full Phoenix still fall back
> to a permanently labelled synthetic fixture unless a matching snapshot exists.

## Quick start

```bash
npm install
npm run dev
```

Open <http://localhost:3000>. The overview leads to the complete workflow; the
original analytical workbench is preserved at <http://localhost:3000/planner>.

Live demo: **<https://heat-priority-engine.vercel.app>** — keyless and read-only.
It serves the committed real Downtown pilot snapshot and cannot spend a credit.

a page render can call FortyGuard at all.

## Product workflow

| Module | Decision it supports |
|---|---|
| **Overview** | What needs attention now, and what may safely be claimed? |
| **Heat monitor** | What did FortyGuard return at each stored Phoenix hour? |
| **Priority planner** | Which stops should be inspected first under a fixed capacity? |
| **Inspection missions** | Which selected stops have been assigned and completed? |
| **Evidence review** | Which field observations may enter the reviewed evidence set? |
| **Scenario lab** | Does the plan outperform simple, legible baselines at K = 10, 20, 50? |
| **Reports & audit** | Can a reviewer reproduce, challenge, and export the decision? |
| **Data & methodology** | Which assumptions, hashes, gates, and blocked claims govern it? |

The closed loop is deliberately explicit:

```text
stored FortyGuard evidence → priority plan → inspection mission
→ field observation (demo-labelled) → human review → plan version → audit package
```

No official seal, flag, agency logo, or endorsement is used. This is an
independent pilot designed to look credible because its evidence boundaries are
visible, not because it imitates a government product.

## The result

> **3 robust priorities + 7 assumption-dependent candidates**
> *(weekday, Downtown Phoenix API pilot, capacity 10 — `CACHED REAL DATA`)*

The real pilot resolves to `EXPOSURE_ONLY`: the confirmed absolute heat is
operationally relevant, while weak spatial differentiation and a non-persistent
held-out anomaly prevent any hotspot claim. That gate decision is part of the
result, not a caveat added afterwards.

The split is the output, not just a list of 10. A selection is **robust** only when
it can be evaluated under all 324 scenarios **and** is chosen in every one of
them. Anything else is in the plan because of a setting nobody has observed.
Analyst pins are counted in neither: a pin is an instruction, not a finding, and
it carries no robustness claim.

An export is a **frozen representation of a completed run**, not a second
execution. The browser sends the `runId` it is attesting to; the server looks that
run up, appends the attestation and export records to the audit trail it already
had, and writes it out. Nothing calls the engine, reads a snapshot or recomputes
an existing timestamp — so the trail says when the analysis happened rather than
when somebody clicked download. A run this server no longer holds is a 409 asking
for a re-run, not a quietly regenerated CSV.

The name recorded is a **named self-attestation**, not an approval: this product
has no authentication, so the name is unverified by construction, and it is bound
to the run id *and* to the digest of the audit trail as it stood when the plan was
reviewed. Every surface says so.

Every selection carries two figures, because neither implies the other:

| Figure | Answers |
|---|---|
| **selection frequency** | in how many *evaluable* scenarios is it chosen? |
| **rank range** | across those, what is its best and worst position? |

A candidate chosen 323 times out of 324 while moving between rank 8 and rank 48
is a different object from one that is always rank 3.

A different day type can produce a different answer because weekday, Saturday
and Sunday use their own GTFS timetables. Weekend ridership is never paired with
a weekday schedule.

## The two metrics

### A — Estimated scenario exposure load · `°C·rider-minutes`

```
ESEL = Σ_hours  riders(h) × expectedWait(h) × max(0, T(h) − 30 °C)
```

A **modelled** quantity under one stated scenario. Every term comes from a source
that publishes what it means:

| Term | Source | Coverage |
|---|---|---|
| Riders | Valley Metro quarterly ridership — average daily riders, by quarter, Weekday/Weekend | 93.07% |
| Wait | Official GTFS → actual departure minutes per route, **per day type** | 99.46% weekday, 98.4% Sat, 98.3% Sun |
| Heat | FortyGuard `/v1/heatmap` (real committed pilot; labelled fixture fallback) | 100% of the 27-stop pilot footprint |

**Not observed riders, not measured exposure.** `riders(h)` is a published
quarterly average pushed through an unobserved hourly profile — nobody counted a
rider at a stop in an hour — and the wait is read off a timetable. The payload
carries `isMeasurement: false` structurally.

**The unit is conditional.** Until the capability probe confirms both the value
field and the unit against a real response, the product refuses to say "°C" and
reports *unconfirmed thermal units* instead. A documented analytic unit says
nothing about which property the response actually returned. For the committed
Downtown pilot both answers are reviewed and bound into the capability
fingerprint ([`docs/fortyguard-capability-report.md`](docs/fortyguard-capability-report.md));
a snapshot captured under different answers is refused, not relabelled.

Nine assumptions (A1–A9), each with what would falsify it, and a 324-scenario
envelope. Waiting time is an expectation over arrivals uniform on each analysed
hour, with each gap **clipped to that hour**; a cap truncates each rider's own
wait before averaging — `E[min(W,c)]`, not `min(E[W],c)`.

### B — Local thermal anomaly · robust `σ`

```
z = ( v − median(cells within 1 km) ) / ( 1.4826 × MAD(same cells) )
```

Is this place hot **for where it is**? Median/MAD because the thing being
detected is what would contaminate a mean-based background. The cell is excluded
from its own background, and top-decile retention matches **cells by position**,
not by z value.

**Validated out of sample** — fitted on the earliest snapshot and checked against
at least two held-out snapshots. The real pilot fails this persistence test, so
the anomaly axis is excluded from its ranking. On fixture runs the same validation
is only an estimator self-check, never a statement about Phoenix.

### Selection — weight-free

Pareto layering on (exposure, anomaly); within a front, order by
`min(exposure percentile, anomaly percentile)`; 400 m minimum separation, relaxed
only if capacity cannot otherwise be filled — and the relaxation is reported.
Domination is strict, so exact ties share a front.

Full detail: [`docs/scoring-methodology.md`](docs/scoring-methodology.md).

## Data modes, and how credits are protected

The thermal layer comes from exactly two places, **neither of which touches the
network**:

| `DATA_MODE` | Meaning |
|---|---|
| `cached_real` | Serve the committed immutable snapshot. Fails loudly if none answers the request — it never falls back silently. |
| `demo` | The labelled synthetic fixture. |
| `auto` | `cached_real` when a snapshot exists, otherwise `demo`. |

There is deliberately **no `live` value**, and **no deployed endpoint** can spend
a credit. Capture is a local CLI that refuses to run when it detects Vercel,
Lambda, Netlify, Cloudflare Pages or CI:

```bash
npm run fortyguard:capture -- --aoi central-phoenix --date 2026-08-03 --dry-run
```

`--dry-run` prints the tile plan and the exact number of billable submissions
without spending anything. Run it first. A real run needs `FORTYGUARD_API_KEY`
and `RUN_LIVE_FORTYGUARD=1` **and** `--confirm-spend` **and** a positive
`--max-new-submissions`, all four on a developer machine, and is protected
these ways:

- a **durable checkpoint** records each activity id the moment the API returns
  it, before any polling, so a crash never loses work already paid for;
- `--resume` polls those activities instead of resubmitting them;
- an **exclusive lock** means a second process refuses rather than buying the
  same tiles twice.

It writes an immutable snapshot with **two** digests. The *surface* hash covers
the values and their positions, and feeds `runId`. The *attestation* hash also
covers provenance, mode, activity ids, field, unit, timezone, the cell rings and
the capture metadata — so a file whose numbers are untouched but whose `dataMode`
was flipped to `LIVE_FORTYGUARD` is refused. Both are re-verified on load. Files
are content-addressed by the attestation digest, written atomically, and never
overwritten. Review, commit, and every later run and export reads it with no
network access.

**Current shipped default: `CACHED REAL DATA`.** The 2024-07-15 Downtown pilot
contains 450 cells from three completed FortyGuard activities. Other AOI/date/hour
requests use the labelled fixture in `auto` mode when no exact snapshot exists.
`cached_real` refuses to fall back.

## What is real, what is not

| Element | Class | Source |
|---|---|---|
| 4,288 active Phoenix stops | **REAL** | Valley Metro, effective July 2026 |
| Ridership on 3,991 of them | **REAL**, documented unit and period | Valley Metro quarterly, FY2024 Q4 — the latest quarter passing *our* completeness checks, which nothing independent reconciles |
| Timetables on 4,265 / 4,218 / 4,215 (weekday / Sat / Sun) | **REAL** | Official GTFS, ODC-BY |
| Scenario exposure load, anomaly, plan | **DERIVED** — modelled, never measured | `lib/metrics/` |
| Heat values | **REAL** for the default Downtown pilot; **SYNTHETIC** fallback elsewhere | Immutable snapshot / `lib/fortyguard/demo-fixture.ts` |
| Shelter presence | **UNKNOWN** for every stop | no usable public source |
| Dollars, people protected, °C reduced | **Not produced anywhere** | blocked by the claim registry |

### Why shelter status is always "unknown"

Phoenix publishes **3,164 sheltered stops** for FY2024-25. The published amenity
fields carry **20** non-null values on the City layer and **0** positive integers
on the Valley Metro layer. Those fields are *incomplete*, not negative — so the
product reports `unknown` for all 4,288 stops and never recommends installing
anything. It prioritises where to look.

## Rebuild the data

```bash
npm run data:fetch      # 4 ArcGIS layers, paginated, count-asserted, hash-recorded
npm run data:gtfs       # GTFS → per-day-type departure minutes per route
npm run data:rebuild    # after data:fetch, re-derive both generated artefacts
npm run data:rebuild-distributed # rebuild GTFS only from the committed ODC-BY archive
npm run data:generate   # join into the application dataset
npm run data:check-distributed # verify the public tree without a network dependency
```

Generated artefacts carry a **canonical hash** with `generatedAtUtc` removed —
the file digest necessarily moves on every run, which made it useless as a
reproducibility target. The joined dataset file digest is checked on every
verification. A complete regeneration requires `npm run data:fetch` because two
raw inputs are deliberately not redistributed; the GTFS derivative still
rebuilds offline on every `npm run verify`.

## Security

- The API key is server-only; `lib/config/server-env.ts` throws if imported from
  client code.
- **No page render can spend a credit.** The public planning endpoint cannot
  reach the FortyGuard API by any path.
- Redaction happens where data leaves the client, so a new call site cannot
  forget it. The key never reaches a log, error, audit record or export.
- Result URLs are fetched only from an explicit host allowlist (SSRF guard).
- CSV exports neutralise formula injection.
- `npm run scan:secrets` and `npm audit --audit-level=high` run inside
  `npm run verify` and in CI.
